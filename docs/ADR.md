## ADR-001: 前端框架选择决策

### 状态
已采纳

### 背景
Crosshair Pro 是一款 Windows 桌面应用程序，需要实现以下核心需求：
- 现代化的用户界面（深色主题、电竞风格）
- 实时预览准心效果
- 低性能开销（CPU<1%、内存<50MB）
- 原生系统集成（系统托盘、全局热键、窗口置顶）
- 快速开发迭代

作为桌面应用，需要在多种技术方案中做出选择，平衡开发效率、性能表现和功能实现。

### 决策
选择 **WPF + .NET 8** 技术栈。

**具体方案：**
- **运行时：** .NET 8
- **UI框架：** WPF (Windows Presentation Foundation)
- **开发语言：** C# 12
- **架构模式：** MVVM
- **DI容器：** Microsoft.Extensions.DependencyInjection

**理由：**
1. WPF原生支持透明窗口（AllowsTransparency）、置顶窗口（Topmost属性）
2. .NET 8提供优秀的性能（AOT编译支持）和低内存占用
3. WPF的XAML数据绑定机制简化UI开发
4. 相比Electron（内存100MB+），WPF应用内存占用可控制在30-50MB
5. 相比WinForms，WPF的DirectX渲染管线更适合透明覆盖层
6. 相比C++/Qt，开发效率更高且无需额外授权费用

### 备选方案

**方案A：Electron + React**
- 优点：
  - 开发效率高，Web技术栈团队可快速上手
  - 热重载支持，UI调试便捷
  - 丰富的npm生态
  - 跨平台能力
- 缺点：
  - 应用体积较大（~80-150MB）
  - 内存占用高（100MB+）
  - 启动速度慢
- 不选择原因：性能不满足低资源占用需求

**方案B：Qt + QML**
- 优点：
  - 性能优秀
  - 跨平台成熟
  - 系统集成完善
- 缺点：
  - C++开发效率较低
  - 商业版需要授权费用
  - UI框架相对陈旧
- 不选择原因：开发效率低，商业授权成本

**方案C：WinForms**
- 优点：
  - 简单直接
  - 学习曲线低
- 缺点：
  - 透明窗口支持差
  - UI现代化困难
  - 渲染性能不如WPF
- 不选择原因：透明覆盖层实现困难

**方案D：Flutter Windows**
- 优点：
  - 现代UI框架
  - 热重载支持
  - 跨平台能力强
- 缺点：
  - Windows桌面端生态尚不成熟
  - 系统集成需要Platform Channel
  - 透明窗口支持有限
- 不选择原因：Windows桌面端成熟度不足

### 影响

**正面影响：**
- 原生Windows体验，系统集成完善
- 性能优秀，内存占用可控制在30-50MB
- 透明窗口实现简单直接
- .NET生态成熟，开发效率高
- 无需额外授权费用

**负面影响：**
- 仅限Windows平台
- 需要用户安装.NET 8运行时
- XAML学习曲线相对陡峭
- UI设计工具（Blend）相对陈旧

### 风险

| 风险 | 级别 | 缓解措施 |
|------|------|----------|
| .NET运行时兼容性 | 低 | 目标.NET 8 LTS版本，提供自包含部署 |
| XAML复杂度 | 低 | 使用MVVM框架简化开发 |
| UI现代化困难 | 中 | 使用第三方UI库（如MaterialDesignInXaml） |
| Windows版本兼容性 | 低 | 测试Windows 10/11多个版本 |

## ADR-002: 覆盖层技术方案决策

### 状态
已采纳

### 背景
准心覆盖软件的核心技术挑战是在游戏画面上显示自定义准心，且需要满足：
- 覆盖层能够显示在全屏游戏之上
- 鼠标点击穿透覆盖层，不影响游戏操作
- 支持 Windows 的全屏独占模式和无边框窗口模式
- 极低的渲染延迟（<16ms，保证60FPS）
- 不触发游戏的反作弊系统

这需要与 Windows 窗口管理系统深度集成。

### 决策
采用 **WPF Layered Window** 方案，配合Windows API调用。

**具体技术实现：**

```csharp
// 窗口属性配置
Window window = new Window();
window.WindowStyle = WindowStyle.None;         // 无边框
window.AllowsTransparency = true;              // 允许透明
window.Background = Brushes.Transparent;       // 透明背景
window.Topmost = true;                         // 始终置顶
window.ShowInTaskbar = false;                  // 不显示任务栏
window.ResizeMode = ResizeMode.NoResize;       // 不可调整大小
window.IsHitTestVisible = false;               // 鼠标点击穿透
```

**Windows扩展样式设置：**
- `WS_EX_LAYERED` (0x00080000) - 分层窗口，支持透明度
- `WS_EX_TRANSPARENT` (0x00000020) - 鼠标点击穿透
- `WS_EX_TOPMOST` (0x00000008) - 置顶窗口
- `WS_EX_TOOLWINDOW` (0x00000080) - 不在Alt+Tab中显示

**全屏模式兼容性处理：**
- 全屏独占模式：部分游戏可能需要特殊处理
- 无边框窗口模式：标准置顶窗口即可覆盖
- 窗口化模式：标准置顶窗口即可覆盖

### 备选方案

**方案A：Direct3D Overlay注入**
- 技术描述：将DLL注入到游戏进程，Hook DirectX的Present方法
- 优点：
  - 完美覆盖任何全屏模式
  - 性能开销极低
- 缺点：
  - **可能被反作弊系统检测为外挂（风险极高）**
  - 技术复杂度高
  - 可能导致游戏崩溃
- 不选择原因：反作弊风险过高，不符合合规要求

**方案B：OBS Overlay技术**
- 技术描述：利用OBS的游戏捕获和覆盖层技术
- 优点：
  - 兼容性好
  - 成熟稳定
- 缺点：
  - 依赖OBS安装
  - 资源占用高
  - 延迟较高
- 不选择原因：增加用户负担，依赖外部软件

**方案C：Windows Composition API (UWP)**
- 技术描述：使用Windows.UI.Composition的Visual Layer
- 优点：
  - 系统原生支持
  - 性能优秀
- 缺点：
  - 仅支持Windows 10+特定版本
  - UWP应用权限受限
  - 全屏游戏覆盖支持有限
- 不选择原因：UWP权限受限，系统集成困难

**方案D：Overwolf平台**
- 技术描述：基于Overwolf平台开发
- 优点：
  - 成熟的覆盖层解决方案
  - 已获部分游戏厂商认可
- 缺点：
  - 依赖Overwolf平台运行
  - 用户需安装Overwolf客户端
  - 平台分成或限制
- 不选择原因：独立性受限，增加用户负担

### 影响

**正面影响：**
- 技术方案安全合规，不读取游戏内存，不注入进程
- 兼容绝大多数游戏的反作弊系统（VAC、BattlEye部分游戏）
- 开发难度适中，可控风险
- 用户体验独立，无需安装额外依赖
- 使用WPF原生功能，代码简洁

**负面影响：**
- 全屏独占模式可能存在兼容性问题
- 某些反作弊系统可能禁止外置覆盖层
- 部分游戏可能使用特殊渲染方式导致覆盖层闪烁

### 风险

| 风险 | 级别 | 缓解措施 |
|------|------|----------|
| 全屏游戏无法覆盖 | 中 | 提供详细设置指南，建议用户使用无边框模式 |
| 反作弊检测 | 中 | 明确告知用户风险，避免Valorant等严格游戏 |
| 窗口层级冲突 | 低 | 持续监控窗口状态，动态调整层级 |
| 游戏更新导致失效 | 低 | 关注游戏更新，及时适配 |

**反作弊兼容性说明：**

| 反作弊系统 | 兼容性 | 建议 |
|------------|--------|------|
| VAC (Steam) | ✅ 通常安全 | 建议使用 |
| BattlEye | ⚠️ 部分游戏禁止 | 需要测试 |
| Easy Anti-Cheat | ⚠️ 部分游戏禁止 | 需要测试 |
| Riot Vanguard | ❌ 禁止 | 不支持Valorant |

## ADR-003: 配置存储方案决策

### 状态
已采纳

### 背景
Crosshair Pro 需要持久化存储用户配置数据，包括：
- 准心样式和参数（大小、间隙、厚度、颜色等）
- 用户创建的预设配置列表
- 快捷键绑定设置
- 游戏关联配置
- 应用偏好设置（主题、语言、启动选项等）

数据特点：
- 数据量小（单个配置 < 1KB，总配置 < 1MB）
- 需要频繁读写（参数调整实时保存）
- 需要支持导入导出
- 需要支持多配置文件管理
- 数据格式需要人类可读（便于调试和用户分享）

### 决策
采用 **JSON文件存储** 方案，存储在用户AppData目录。

**存储目录结构：**
```
%APPDATA%/CrosshairPro/
├── config.json           // 主配置文件
├── presets/              // 预设配置目录
│   ├── default.json      // 默认预设
│   ├── cs2_pro.json      // CS2预设
│   └── valorant_dot.json // Valorant预设
├── custom_images/        // 自定义准心图片
│   └── user_crosshair.png
└── logs/                 // 日志目录
    └── app.log
```

**技术实现：**
- 使用 `Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData)` 获取用户数据目录
- 使用 `System.Text.Json` 进行序列化/反序列化
- 使用防抖机制优化频繁保存（100ms内只保存最后一次）
- 配置变更自动保存，无需用户手动保存

### 备选方案

**方案A：SQLite数据库**
- 优点：
  - 结构化查询，数据关系清晰
  - 支持事务，数据一致性好
  - 大数据量下性能更优
- 缺点：
  - 数据量小时过于复杂
  - 数据库文件需要额外维护
  - 导入导出需要额外处理
  - 增加依赖体积
- 不选择原因：数据量不足以支撑数据库复杂度

**方案B：IndexedDB**
- 优点：
  - Electron内置支持
  - 支持大数据量和复杂查询
- 缺点：
  - API复杂
  - 数据存储在浏览器环境，不易直接访问
  - 数据迁移和备份困难
- 不选择原因：不适合桌面应用文件管理需求

**方案C：Windows注册表**
- 优点：
  - Windows原生支持
  - 系统级存储，卸载后可保留
- 缺点：
  - 只支持键值对，复杂数据需要序列化
  - 不易导出和分享
  - 用户难以查看和修改
- 不选择原因：不适合复杂数据结构存储

**方案D：加密存储**
- 优点：
  - 数据安全性高
  - 防止用户篡改
- 缺点：
  - 用户无法直接查看配置
  - 分享配置需要解密
  - 增加实现复杂度
- 不选择原因：准心配置无敏感数据，加密过度设计

### 影响

**正面影响：**
- 实现简单，代码量少
- 人类可读，便于调试和用户分享
- 导入导出便捷（直接复制文件或分享JSON）
- 无额外依赖，应用体积小
- 跨版本兼容性好（JSON Schema版本控制）

**负面影响：**
- 大量预设时需要遍历文件（但预计不超过100个，影响可忽略）
- 文件损坏风险（可通过备份机制缓解）
- 并发写入需要处理（单进程应用，风险较低）

### 风险

| 风险 | 级别 | 缓解措施 |
|------|------|----------|
| 配置文件损坏 | 中 | 每次保存前备份，启动时校验JSON有效性 |
| 版本升级兼容性 | 中 | 使用版本号控制，提供迁移脚本 |
| 用户误删配置 | 低 | 提供配置恢复和默认配置重置功能 |
| 多实例并发写入 | 低 | 单实例限制，文件锁保护 |

## ADR-004: 热键系统方案决策

### 状态
已采纳

### 背景
Crosshair Pro 需要全局热键支持，让用户在游戏中无需切出即可控制准心：
- 显示/隐藏准心（Ctrl+Shift+X）
- 切换预设配置（Ctrl+Shift+1-9）
- 重置准心位置（Ctrl+Shift+R）
- 调整准心大小（Ctrl+Shift++/-）
- 锁定准心位置（Ctrl+Shift+L）

核心需求：
- **全局响应：** 即使游戏在前台也能响应
- **低延迟：** 热键触发到响应 < 100ms
- **可自定义：** 用户可修改快捷键绑定
- **冲突检测：** 检测系统级快捷键冲突

### 决策
采用 **Windows Raw Input API + RegisterHotKey** 方案。

**技术架构：**
```
┌─────────────────────────────────────────┐
│           HotkeyManager                 │
│  - 注册/注销热键                        │
│  - 解析快捷键字符串                    │
│  - 触发热键回调                        │
│  - 冲突检测                            │
└─────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────┐
│       Windows Raw Input API             │
│  (底层键盘输入捕获)                     │
└─────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────┐
│          Win32 API                      │
│  RegisterHotKey / UnregisterHotKey      │
└─────────────────────────────────────────┘
```

**技术实现：**
1. 创建隐藏消息窗口接收WM_HOTKEY消息
2. 使用RegisterHotKey注册全局热键
3. 解析组合键字符串（如"Ctrl+Shift+X"）
4. 提供冲突检测功能

### 备选方案

**方案A：WPF内置热键**
- 优点：
  - 实现简单
  - WPF原生支持
- 缺点：
  - **关键问题：游戏前台时可能无法响应**
  - 无法区分左右修饰键
  - 功能受限
- 不选择原因：游戏兼容性不足

**方案B：Windows Raw Input API直接实现**
- 优点：
  - 底层访问，性能最优
  - 可以处理管理员权限的游戏
  - 完全控制输入处理
- 缺点：
  - 需要使用C++编写Native Addon
  - 实现复杂度高
  - 需要处理键盘设备枚举和低级事件
- 不选择原因：开发成本高，RegisterHotKey已足够

**方案C：AutoHotkey集成**
- 优点：
  - 热键功能成熟完善
  - 支持复杂的脚本逻辑
- 缺点：
  - 需要额外打包AHK运行时
  - 用户可能被杀毒软件警告
  - 跨应用通信复杂
- 不选择原因：不适合正式产品集成

**方案D：第三方热键库**
- 优点：
  - 封装好的实现
  - 使用简单
- 缺点：
  - 维护状态不确定
  - 游戏兼容性需要测试
- 不选择原因：可控性不如直接使用Win32 API

### 影响

**正面影响：**
- 游戏前台时热键响应可靠
- 支持复杂的组合键逻辑
- 可区分左右修饰键（如需要）
- 冲突检测可实现
- 性能开销低（< 1% CPU）
- 实现相对简单

**负面影响：**
- 低级键盘钩子可能被安全软件警告
- 需要处理WM_HOTKEY消息循环
- 不同键盘布局需要适配

### 风险

| 风险 | 级别 | 缓解措施 |
|------|------|----------|
| 权限不足时热键失效 | 高 | 启动时检测权限，提示用户 |
| 安全软件拦截 | 中 | 申请代码签名，提交白名单 |
| 热键冲突 | 中 | 提供热键冲突检测和修改提示 |
| 键盘布局兼容性 | 低 | 使用虚拟键码而非字符码 |
